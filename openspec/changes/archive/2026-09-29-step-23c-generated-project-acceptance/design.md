## Context

See `proposal.md`. The 23A generator has a complete ownership inventory and deterministic output, but its root and site package files reference unpublished `@lacecms/*@0.0.0` versions. The packages are private and use `workspace:*` and catalog dependencies. `apps/api/Dockerfile` and `apps/builder/Dockerfile` build engine images from this repository; `apps/api/src/project-config.ts` resolves the repository root config by default. The generated Compose template has image placeholders but omits the explicit migrate/init/dispatcher and source/output wiring used by the repository's production Compose. The generated site currently fetches content at Astro build time. 23B supplies guarded operator commands and schema readiness.

## Goals / Non-Goals

**Goals:** Run a disposable, isolated consumer installation and full product journey; retain exactly the 23A ownership model; turn generated Node and Compose commands into usable paths; make CI produce a clear pass/fail result with no credential spill.

**Non-Goals:** Publish to npm or an image registry, vendor source into the starter, run remote Cloudflare D1/R2 or Pages deployment, introduce a second sync policy, implement upgrade behavior, or replace the source workspace's existing production deployment.

## Decisions

1. **Pack and install outside the monorepo.** Build the required packages, pack the complete runtime dependency closure into a temporary directory, and copy the tarballs into a test-only directory under the disposable generated project. Rewrite only that project's dependency references to relative `file:` tarballs, so its frozen lockfile remains portable when the builder copies the project into its container. Inspect the installed dependency graph and resolved real paths, rejecting links into the source checkout. Never write local tarball paths into checked-in templates or contract fixtures. A local registry would test publication behavior too, but adds a service and leaves more state to clean up.
2. **Make the API image consume user configuration without copying source into the project.** Mount the generated `lace.config.ts` read-only into the versioned API image's documented config location for API, migration/sync, and dispatcher roles. Keep the package resolution base inside the image, where engine dependencies are installed. The generated local Node path runs API and MinIO from images while Astro and the operator CLI run from the installed generated project. Avoid mounting the whole generated project over the image's workspace because it would hide packaged runtime files and blur ownership.
3. **Align generated Compose with the existing production flow.** Extend the generated template to run MinIO initialization, explicit one-shot migration, API, dispatcher, builder, and static serving with a project-local SQLite data mount plus named MinIO/output volumes and bounded health checks. The project-local SQLite path lets the tarball-installed operator CLI and the container API use the same database without copying it; it is ignored by Git. Use locally built tagged images for acceptance, supplied through variables; no generated image build context points at the source checkout. Mount the complete generated project read-only to the builder and provide a writable output volume. The fixed-command builder currently accepts only `apps/site` in the source monorepo; make it recognize exactly the monorepo or generated `site/` layout and use a fixed, layout-specific install/build path, with no request-controlled command or path. Keep API migration explicit and readiness gated by schema state. Reuse existing image code, not copied engine source.
4. **Drive real public interfaces.** Run the 23B CLI from the generated project's installed packages. Use HTTP setup/login and content endpoints for the admin journey, then build Astro from the generated site and assert rendered published text. A browser UI pass is optional diagnostic coverage; the acceptance contract is the authenticated public behavior. Use one test-owned email/password and setup token; redact them from captured command/HTTP failures and reveal the token only at the designated bootstrap assertion.
5. **Treat optional Cloudflare as a separate local proof.** Generate a second project with `--cloudflare`, build its Astro/Pages output, validate its workflow/config references, and run a local Worker/D1 smoke using the existing Worker bundle and Miniflare test path. This proves template compatibility without remote account credentials or pretending the Pages template contains the CMS Worker source.
6. **Snapshot only stable inputs.** Store a sorted generated-tree inventory and exact manifest plus managed file digests for both variants, using a fixed generated project name. Ignore install outputs, `.env`, lockfiles created by test installation, timestamps, ports, and absolute temporary paths. Compare two regenerations and the committed fixture before rewriting disposable package references. This catches template drift while allowing the acceptance harness to install tarballs.
7. **Bound execution and cleanup.** Use a unique temporary parent, Compose project name, ports, and environment file; always stop processes and run `docker compose down --volumes` in `finally`. Skip no required stage silently: missing Docker or packaging support is a failed acceptance prerequisite, while ordinary unit and quality gates remain separately runnable. CI runs the full acceptance job on a Docker-capable runner after build; a local command reports each stage and the first failing stage.
8. **Build the generated MinIO service from pinned source.** The original Compose image on Quay became inaccessible to fresh anonymous pulls after local acceptance had passed with a cached copy. Bundle a small Dockerfile in the managed deployment template, build the same pinned MinIO release from its public source tag, and use that build for the generated service. Keep the build context limited to the deployment directory so installed dependencies and project content are not sent to Docker. The acceptance runner must explicitly rebuild this service from a cold image state before exercising Compose, and the generated operations guide must state the source-build prerequisite.

## Risks / Trade-offs

- [Private packages, `workspace:*`, or catalog ranges make tarballs uninstallable] → Repair pack metadata in the affected package graph, then require the out-of-workspace installation and graph audit to pass; do not use symlink fallbacks.
- [Builder's original `apps/site` assumption rejects the generated layout] → Recognize only the two trusted layouts and verify both with the fixed-command builder tests; reject all other layouts before executing pnpm.
- [The API image's config location or compiled path changes] → Expose one documented config path and verify it with a generated-project smoke; keep mount read-only.
- [Compose build consumes more CI time and network] → Build image tags once per acceptance run and use bounded health/timeouts; preserve clear stage logs and guaranteed cleanup.
- [A registry removes a previously public MinIO image] → Build the generated MinIO service from the pinned source release and verify a fresh local build in acceptance; source and Go module availability remain explicit network prerequisites.
- [Secrets appear in subprocess output] → Capture and sanitize diagnostics through a single runner, avoid shell tracing, and assert sentinel values never appear outside the designated bootstrap result.
- [Cloudflare local smoke cannot prove remote deployment] → Label it local bundle/smoke coverage; remote deployment remains release operations work.

## Migration Plan

No database migration is added. Existing generated projects can regenerate the 23C templates only while still empty or receive future managed-file updates through Step 24. The acceptance harness and fixtures can be reverted independently of persisted runtime data. Image coordinates remain environment-supplied until the release channel is chosen.
