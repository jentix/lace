## Why

Step 14, Session 14B completes the live local Astro example: a contributor can currently publish content, but the site only demonstrates the original home and blog routes. A repeatable proof is needed that code-defined models, admin editing, publication, the published API, and additional Astro URLs work together without fixture edits.

## What Changes

- Add an `about` singleton page at `/about` and a `notes` collection at `/notes/:slug` to the root configuration, each with a matching user-owned Astro route using the existing block renderer.
- Extend the site export projection and fixture so the additional routes are generated only from published entries. Keep one SDK build-export read per live site process and preserve the starter routes.
- Add a browser-level local flow covering sync, admin draft editing, publication, published-only API output, generated pages, and a later unpublished draft.
- Accept the Admin editor's ULID-format stable block keys in content validation so authored blocks can be saved and published in that flow.
- Document the repeatable page, collection, field, and block workflow, including version rules and the required API/site restart steps.

## Capabilities

### New Capabilities

None.

### Modified Capabilities

- `astro-reference-site`: The reference site also generates code-owned `/about` and `/notes/:slug` routes from published export entries, with draft isolation and the existing block renderer.
- `local-node-development`: The local workflow demonstrates new model synchronization through admin publication and a site refresh, and documents the config version rules for further additions.
- `block-registry`: Ordered aggregate validation accepts stable ULID-format block keys generated by the accepted Admin editor contract.

## Impact

This depends on completed Sessions 13A, 13B, and 14A. It affects `lace.config.ts`, `apps/site`, content validation, local developer documentation, and integration verification. It does not add CMS route generation, change the public API or SDK, alter token permissions, or introduce automated build dispatch. The design follows architecture sections 4.2, 4.4, 4.7, 5, and 6 and the accepted `astro-reference-site`, `local-node-development`, `block-registry`, `content-model-configuration`, and `public-sdk` specs.
