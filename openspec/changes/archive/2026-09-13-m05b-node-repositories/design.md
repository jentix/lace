## Context

See [proposal.md](./proposal.md) for motivation. Session 5A supplies the shared
SQLite schema and a Node connection factory; Session 4 supplies portable
aggregate and port contracts. The architecture requires a draft save to rebuild
the relational media-reference projection atomically, a public projection that
never exposes drafts, and behavior that Cloudflare D1 can later match.

## Goals / Non-Goals

**Goals:**

- Add Node adapter implementations for portable read ports and the create/save
  subset of draft commands.
- Keep every write that changes a complete draft inside one `better-sqlite3`
  transaction, with explicit revision guards and domain-error mapping.
- Add a typed, validated media-reference projection to the portable save input,
  generated by the application layer from known field definitions.
- Make SQL access bounded and set-based, with portable row-to-domain mapping.

**Non-Goals:**

- Guarded publication, deletion, outbox/site-build records, model sync, media
  upload/storage, REST handlers, or D1 adapter work.
- A generic transaction callback, database schema migration, JSON-path querying,
  or public binary streaming.

## Decisions

### Split Node read/public/draft repositories by capability surface

`@lacecms/platform-node` will expose Node adapters that implement the existing
read and public-read ports and the create/save draft-command subset. The draft
surface deliberately has no `publish` method; Session 5C adds that specialized
operation separately.

Alternative considered: one all-purpose repository exposing every future
mutation. Rejected because it would make publication callable before its
guarded, idempotent transaction exists.

### Permit Node adapters to consume portable value packages directly

The source-level dependency graph will permit `@lacecms/platform-node` to import
`@lacecms/domain` and `@lacecms/content` through their public entry points. The
adapter needs domain constructors and JSON types to map SQLite rows to the
portable values required by `@lacecms/application`; these are downward edges,
and neither portable package imports a platform package.

Alternative considered: relocate mapping into `@lacecms/db`. Rejected because
the shared SQLite/D1 schema package would then own Node runtime behavior and
would make the future D1 adapter depend on a Node-driven mapper.

### Let application validation produce media-reference rows

`CompleteDraftMutation` will include an immutable list of validated references.
`ContentUseCases` derives it from the normalized model fields and normalized
block fields: snapshot fields use `$fields`, block fields use the stable block
key, and field names become field paths. The repository consumes these rows
directly; it never scans arbitrary JSON values for strings that happen to match
media IDs.

Alternative considered: recursively inspect JSON in the Node adapter. Rejected
because it cannot distinguish a media value from an unrelated string, diverges
from configuration validation, and cannot be reproduced reliably by D1.

### Use strict, versioned seek cursors

The adapter will encode one versioned base64url JSON shape per list order and
validate decoded structure, safe integer timestamps, non-empty IDs, and list
kind before binding it. Requests fetch `limit + 1` rows with a capped positive
limit; the final row is retained only as the next boundary. SQL uses lexicographic
seek predicates matching the exact `ORDER BY`, avoiding offset scans and making
timestamp ties deterministic.

Alternative considered: opaque signed offsets. Rejected because offsets drift
under writes and cursors are query boundaries rather than authorization claims.

### Hydrate aggregates in bounded set queries

For an entry, the adapter will load the entry/model/snapshot pointers and then
load the at-most-two referenced snapshots' blocks in one ordered query. For
public pages and build export, it will load current published route/snapshot
rows and fetch all participating blocks with a bounded `IN` query (chunked when
needed for SQLite parameter limits), then group and map them in memory. Public
media visibility uses an indexed `EXISTS` relation from a current published
snapshot instead of inspecting draft rows.

Alternative considered: ORM relation loading per entry. Rejected because it
creates N+1 query behavior and obscures bounded-query review.

### Write create and save through explicit SQLite transactions

Creation inserts the entry, its draft snapshot, blocks, and projection rows,
then sets the draft pointer in one transaction. A save first guards the draft
row by identity and expected revision, replaces blocks and reference rows, and
updates values plus revision once. All statement failures abort the transaction;
SQLite constraint errors and zero-row revision guards map to stable domain
failures.

Alternative considered: one statement per operation without a transaction.
Rejected because an interrupted block/reference replacement could leave a
partial draft aggregate.

## Risks / Trade-offs

- [SQLite parameter limits can constrain block/reference batches] → cap portable
  input at existing limits and chunk only independent bulk inserts inside the
  same transaction.
- [Corrupt JSON already in storage cannot be mapped to a valid domain aggregate]
  → fail closed with the stable invalid-content state rather than exposing a
  partial public result.
- [Published public-media authorization needs an exact current-snapshot join] →
  test draft-only, former-publication, and current-publication cases explicitly.
- [Synchronous SQLite calls sit behind async ports] → adapters return resolved
  promises while retaining one synchronous transaction boundary.
- [A broadened adapter edge could hide an accidental reverse dependency] → keep
  the boundary checker cycle detection and add a focused allowed-edge assertion.

## Migration Plan

1. Extend portable application values and use-case projection generation,
   retaining the existing Session 5A schema.
2. Add Node cursor codecs, mappers, bounded readers, and transactional draft
   writer with focused temporary-file SQLite tests.
3. Run focused tests, root quality gates, and strict OpenSpec validation. Deploy
   only after the explicit Session 5A migration has been applied; rollback is an
   application-package rollback because this session creates no migration.
